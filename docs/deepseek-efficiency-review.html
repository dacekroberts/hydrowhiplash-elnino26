DeepSeek Efficiency Review

How the Claude-plans, DeepSeek-builds setup performed on one change to an existing codebase: eight modules print a report of the pinned input files they replaced after a guarded rebuild.

The build was correct on the first run. Getting it started cost more than the build did.

One implement run on deepseek-flash changed 10 files in 17 minutes with no retry, stayed inside its allowed files, and passed every check Claude ran, including one the worker never saw. No defect was found. The 31 minutes between the owner's approval and the worker starting went on two refused starts and a failed shell command.

What this pilot cannot say is whether the setup saves money or time. The run's token counts were not logged, and Claude's own time on the plan and the checks is not measured.

Why it went the way it did, and what that hides

  • The plan was 640 words for 465 added lines, the lowest ratio of plan to code in the ledger. It was written as a goal with acceptance tests, and it left five things unsaid on purpose: that a stamped run prints nothing, that one module's two guards give one report, a lazy import, which files of a download folder count, and how to test a command that calls the network. The worker handled all five correctly.
  • The change itself is small and repetitive. 415 of the 465 added lines are one test file. The source change is about 50 lines: two short helpers and one call in each of eight modules. So "465 lines" overstates the difficulty.
  • It took 65 turns, the most in the ledger, for that small source change. The worker had to read eight modules to find where each write happens, which is the part the plan did not spell out.
  • This was not the pilot the handoff first described (one of the run safeguards, before the registered runs). The safeguards stayed with Claude; this task was chosen for after the runs. It tests reading an existing codebase, not code a result depends on: no number, table or pinned input can change through it.
  • Claude's time and tokens on the plan and the checks are not measured, so there is still no baseline for whether Claude alone would have been cheaper.

Where the system was inefficient

  • The start was refused twice. Claude Code's permission check refused the session starting the worker, on 12 October and again on the 13th. The owner had to start it in a terminal. That is a deliberate guardrail and was not worked around, but it turned a one-step start into a handover.
  • The first handover command failed. The command given to the owner used a shell redirect that PowerShell does not accept. A small launcher script, called through Git Bash by its full path, fixed it. Approval to start: 31 minutes (07:01 to 07:32 UTC).
  • No token counts. This run's line in the run log has no token fields, so its cost is unknown. The line was written by the session after the owner-started run, not by the wrapper.
  • The staged copy. The project's data must stay out of the worker's reach, so the build ran on a copy holding code only. Six existing tests fail there for want of data, so the check is a before-and-after count, not a green suite. One of them left an empty file under the copy's data folder.
  • Turns against size. 65 turns and 17 minutes for about 50 lines of source is slow next to the earlier builds, though those ran on a different model.

Changes to make to the delegation skill

  • When the session cannot start the worker, have the skill write a launcher script and give the owner one command for their shell: on Windows, Git Bash by its full path. No redirects in a command meant for PowerShell.
  • Make the wrapper write the run-log line, tokens included, however the run is started. If the session has to add the line itself, it should take the token counts from the wrapper's output or write unknown in those fields.
  • Add to the plan template for a staged copy: the count of tests that pass and fail before the build, and which failures are expected, so the worker and the check use the same baseline.
  • Add a cleanup step: after the tests, list files created outside the allowed paths in the copy and remove them.

Recommendation

Keep the goal-plus-acceptance-tests plan style for changes of this kind. The worker found the five unstated points, and the checks stayed mechanical.

Fix the start first: a launcher script by default when the session's start is refused, and a run-log line with tokens whoever starts the run. Then the next review can give a cost.

Next test: a change where the source, not the test file, is most of the work, and one result-bearing check that a wrong build would fail.
